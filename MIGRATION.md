# Migration plan: evolving `club` into the new architecture

> Agreed 2026-10-21. Instead of replacing this app with the from-scratch rewrite in `C:/dev/src/club-next`, we convert **this** app gradually. It stays live and usable every session night throughout. `club-next` becomes a **reference**: its decisions, tested rules code, components and user stories are carried over piece by piece. It will probably be archived once nothing more is needed from it.

---

## How we work (with Claude)

- **One step per session, PR-sized.** Each step leaves the app working, can be reverted on its own, and is either *structural* (nothing visible) or *visible* (players notice). Aim to alternate, so the effort keeps paying off.
- **Plan first, every step.** At the start of a step Claude proposes:
  - what changes;
  - what gets copied from `club-next`, with exact file paths;
  - how it will be tested;
  - how it would be rolled back.

  Nothing is built until the developer approves.
- **This file is the shared memory.** Update the step table below at the end of every step (status, what was done, anything learned). Decisions made along the way go in the "Decisions log" at the bottom (or in `club-next/decisions.md` until that's archived). Keep `AGENTS.md` accurate about the *current* state of the app.
- **Safety rules:**
  - Work on a branch. Deploy to **staging** (`npm run deploy:staging` in `worker/`) first.
  - Before any schema change, refresh staging from prod (the GitHub Action) and rehearse the migration on real data.
  - Run the browser checks against staging (Playwright, ported from `club-next/e2e/`).
  - Claude may deploy to staging and prod as required.
  - Every prod schema change has a backup first (`wrangler d1 export club-prod --remote`) and a written rollback (D1 Time Travel and/or a down-migration). Worker code rollbacks use `wrangler rollback`.
- **HelloClub writes** stay exactly as they are today (the existing sync) until a step explicitly changes them. Any *new* HelloClub write behaviour runs in dry-run on staging first.
- **Priorities are decided ad hoc.** The order below is a sensible default, not a commitment. The visible changes list is a menu to pick from.

## Follow-ups (not steps, but don't lose them)

- ✅ **Data backups beyond 7 days** (built 2026-10-23; see AGENTS.md, Backups). D1 Time Travel covers the last 7 days. A nightly GitHub Action (`backup-prod.yml`, about 3am NZ) exports prod, leaves out sign-in sessions/verification rows and blanks account tokens and passwords, and commits the dump to the **private** repo `seminolas/club-backups` (git history keeps every night). It pushes with a deploy key limited to that repo (`BACKUPS_DEPLOY_KEY`) rather than a personal token. The restore drill is the staging refresh with source `backup`.
  - Considered and not chosen: **R2** (Cloudflare's own suggestion). Its free tier (10 GB-month storage, 1M writes, 10M reads a month, free egress) easily covers a ~1 MB nightly dump. Activating it reportedly asks for a card or PayPal as verification, charging only beyond the free tier (per third-party guides; check the dashboard). For: stays in Cloudflare, no GitHub token, lifecycle rules can expire old dumps. Against: a payment method on file with no hard spending cap, and plain files rather than a browsable, diffable history. Cloudflare only offers alerts, not caps (budget alerts by dollar amount; R2 usage notifications by bytes/requests). If we choose R2: private bucket, an API token that can only write to that bucket, and a $1 budget alert.

- **A known bug, deliberately not fixed yet** (the requirements may change; see AGENTS.md, Known issues): a ladder import while a session is open doesn't show. Revisit with ladder import. (The other one, deleting a player with a login or role but no game data failing, went away in S4b: 0012 dropped the tables that blocked it.)

- **Sync runs and background jobs: thinking so far (2026-10-23, nothing decided).** Revisit when planning S7/V10.
  - **No job engine for now.** Cloudflare Workflows (started by Cron Triggers) is the off-the-shelf equivalent of JobRunr (per-step retries, saved state, runs visible in the dashboard), but it's more than we need yet. Plain Cron Triggers first; move a job to Workflows only if it outgrows one invocation (check the free plan's subrequest limit, about 50 per invocation, and Workflows/Queues limits at the time).
  - **The attendance sync stays synchronous** (admin clicks, results in a few seconds; that immediate feedback is wanted). What's missing is a *record*: `sync_runs` (id, kind `attendance`/`members`, started by an admin or the schedule, session, times, status, summary) and `sync_results` (run id, player, ok/failed, error). The run id goes into log lines so "why did it fail" is one search in Cloudflare's logs. Consistency comes from every sync writing the same run record, not from one job runner. Check whether the sync currently calls HelloClub from the browser; if so, move it to a Worker route that writes the record and returns results straight away.
  - **UX idea:** a sync status column on the session's players (latest result per player: Synced / Failed with reason / blank), a "Failed" filter, then select and "Sync again". Belongs to the new players table (the table-and-actions UI being prototyped in `club-table-lab`).
  - **Member sync, split in two:** (1) *linking data only*: HelloClub members' ids, emails and Google ids in a separate table (e.g. `hc_members`), never creating players; used only to auto-link sign-ins. No UI and no effect on the ladder, so it could come before the new UI. (2) *creating or updating players* from HelloClub would add non-ladder people, so it waits for the new UI (how new and inactive people are shown).
  - Order when ready: run-record tables, then the attendance sync writing them, then the status column and filter in the new UI.

- **Parked sign-in methods** (2026-10-22: Google only for now, the others "too much trouble" for the moment): one-time email codes (BetterAuth `emailOTP`, needs Resend + DNS on a sending domain), admin-issued single-use sign-in links (e.g. shared on WhatsApp), Facebook (needs a Meta app; per-app ids, sometimes no email), passkeys. Only 2 regular players were Facebook-only on HelloClub (Martin Hedlund, Tricia Liew). Also parked: fetching members' HelloClub sign-in emails (`profiles`) to improve auto-linking; revisit with a scheduled HelloClub sync (S7).

- **Profile photos (future):** BetterAuth saves the Google photo (`user.image`) only when an account is created, so the 88 accounts migrated in 0011 have none. If the S5 user menu shows photos, refresh `user.image` on each sign-in (initials as the fallback).

## Decisions log (migration-specific)

- **2026-10-21:** Gradual migration of `club` instead of switching to the rewrite. The developer tested `club-next`, liked the direction, but wants to proceed step by step on the live app. A frontend build step is OK from S1. What happens to `club-next` will be decided later (probably archived).
- **2026-10-21 (S1):** Set validation accepts any of 21-, 15- and 11-point sets (real sessions mix them), instead of `club-next`'s single points-per-set setting; a per-club setting can come with V8.
- **2026-10-21 (S1):** Live box standings count a game as won only once it's finished, and ignore games with an invalid score until fixed (before: a 1–0 lead counted as a win, invalid scores counted). The one visible change in S1. Closing is unaffected (it needs every game finished).
- **2026-10-21 (S1):** Where the live app and `club-next` disagree, the live app's behaviour wins unless agreed otherwise. Kept from the live app: a match with a half-entered set is "in progress" even if another set is invalid; custom box layouts (`parseBoxLayout`), which `club-next` lacked.
- **2026-10-21 (S1):** Tie-break for players not on the ladder-before is moot: the app only adds players during attendance, straight onto the ladder, so it can't happen.
- **2026-10-21 (S1):** Lint and formatting apply to `worker/` only; `js/` and `index.html` stay as they are until S5 replaces them.
- **2026-10-21 (S2):** The SQL migrations in `worker/migrations` stay the source of truth for the schema; `worker/src/db/schema.ts` mirrors them for typed queries, with a test that fails on drift. How new schema changes are written (by hand, or generated with `drizzle-kit generate`) is decided when S3 is planned.
- **2026-10-21 (S2):** Database tests run on a real local D1 (wrangler's `getPlatformProxy`) rather than better-sqlite3, so they use the same engine as prod. Fixtures use made-up names because the repo is public.
- **2026-10-21:** A reusable table + actions component is being designed separately in `C:/dev/src/club-table-lab` (its own repo; `club` and `club-next` are read-only there). When accepted, its `HANDOVER.md` describes how it's adopted in S5.
- **2026-10-22 (V1, planned):** Players sign in with **Google only** for now. On sign-in: an already-linked login is done; otherwise auto-link when exactly one unlinked active player's HelloClub email (`players.email`) matches the Google email (case-insensitive; shared emails don't auto-link); otherwise "This is me": pick yourself from the unlinked active players, linked immediately, no approval (admins can unlink). Not on the list: ask an admin. Signed-in players get no new behaviour yet; that comes with V2/V3. The header shows plain text ("Signed in as <first name> · Sign out"); the standard avatar + user-menu component (Mantine `Avatar` + `Menu`) comes with the new UI in S5, not as a stop-gap in the Alpine app. The admin player page shows the linked Google account with Unlink.
- **2026-10-23 (V1):** To use the app you must be a known player: matched by email or picked through "Which player are you?" (open to every unlinked active player, HelloClub-linked or not). **Admins too** (staging's Test Admin has its own player). The box can't be skipped; newcomers see "New here? For now, an admin needs to add you." until V17 lets them join from the app (HelloClub's sign-up has proven a hurdle, so V17 creates the HelloClub member for them rather than sending them to HelloClub).

Scope: score writes only; other admin actions stay REST and tell screens to reload. Everyone viewing gets live updates, signed in or not.
